## 実装順序

| 段階 | 内容 | 次へ進む条件 |
| --- | --- | --- |
| 0 | 基準コードと既存変更の照合 | 採用する基準SHA、保全した差分、各指摘の残存箇所が明確 |
| 1 | 本人用機能の依存・契約を整合（R1） | 型チェックとビルドが成功し、ローカル画面を操作できる |
| 2 | 詳細編集の保存・競合を修正（R2） | 通常保存が成功し、古い版・欠落した版で状態が変わらない |

## 0：基準コードの整合

1. ルートと入れ子のチェックアウト、現在の変更、Codexに付いている作業ツリーを確認する。作業中のファイルと起動中の開発サーバーを保全する。
2. `origin/main` を取得し、引き継ぎに記録されたPR #2/#3/#5/#6の現在の状態・コミット・差分を確認する。履歴にある「未マージ」「デプロイ済み」を現時点の証拠として扱わない。
3. 適切な既存作業ツリーを再利用するか、必要なら最新mainから隔離した作業ツリーで修正する。ブランチ名は `codex/` を使う。元の未コミット変更は保存・照合して必要な差分だけを反映する。
4. 本人用機能、カレンダー、開発CSP、ICS、Firestoreの競合リトライについて、取り込み済み・未反映・今回修正が必要な差分を一覧にする。既存の修正を落とさない。
5. R1〜R4を基準コードで再確認する。既に修正済みの指摘はテストで確認し、残存する指摘だけを変更する。

成果物：採用SHAと差分一覧、作業パス、指摘ごとの対応状況。現在の壊れた作業ツリーから不足ファイルだけを推測して再構築することを起点にしない。

## 1：依存・表示・フラグの整合

- `config/product.ts`：既存仕様の本人用5テンプレート、支援する方への定型4種、`recipientAccess` フラグを整合する。
- `types/domain.ts`、`services/contracts.ts`：本人用入力・表示型、サービス契約、ページの任意項目、主催者表示のrevision等を揃える。既存DBにない任意項目は表示側で空配列・false・revision 0へ正規化する。
- `services/factory.ts`：同じDocumentStoreを使う `recipientService()` を整合する。Auth、Firestore REST、通知プロバイダーの方式は既存契約を維持する。
- `app/dashboard/[id]/page.tsx`：サーバーで評価したフラグを `DashboardDetail` へ渡す。OFFでも通常の管理画面・カレンダーを操作できることを確認する。
- `components/support-page.tsx` 等：お休み中の表示、定型、買い物の立て替え案内を既存要件どおりに整合する。非公開欄・連絡先・トークンを追加しない。
- `.env.example`、`wrangler.jsonc`、`app/robots.ts`、`next.config.ts`：フラグ既定OFFと本人用URLの検索・キャッシュ制御を整合する。本番のフラグ値やSecretsは変更しない。

検証：欠落export・型エラーを解消し、本人用unitを含む既存テストとビルドを通す。ローカルON/OFFで管理UI、本人用URL/API、公開画面を確認する。

## 2：保存のrevisionを一貫させる

- `components/wizard.tsx` は編集開始時に取得した `existing.revision` を保持し、PATCHの `baseRevision` に送る。保存直前に最新版へ読み替えて競合を隠さない。
- `app/api/pages/[id]/route.ts` の必須整数検証を維持し、`SupportService.save()` とサービス契約でも版指定を必須にする。直接呼び出すテスト・スクリプト等を検索して整合させる。
- 409時は入力を保持して、予定が更新されたことと再読み込みの必要を案内する。古い入力で自動再送しない。
- 旧DBのrevision未設定はサービス側で0と扱う。正常保存・追加・取り消しで予定一覧が変わる場合は同じcommitで増やす。

回帰テスト：通常編集200、revision欠落・不正400、古い版409、本人の追加／取り消し／主催者カレンダー追加後の保存拒否。拒否前後の予定・秘密情報・revisionが一致することを確認する。現在の調査用テストは誤動作を期待しているため、そのまま合格条件として移さず、望ましい挙動のテストを正式なtestsへ置く。

## 3：本人用リンクの終了と取り消し

### 終了の判定（R3）

本人用トークンからページを読む共通処理で、削除中・archived・closed・`endDate < todayJst()`・トークン不一致を拒否する。JSTの終了日当日は利用可能、翌日から利用不可とする。Cronがまだページをclosedへ更新していなくても期間終了を拒否する。

`view()` はnull、本人用APIは404を返し、追加・取り消し・設定変更で書き込みを行わない。判定は変更トランザクション内でページを読んで行う。下書きで発行済みリンクを表示する既存挙動と、担当管理トークンは別に維持する。

回帰テスト：手動終了、期間終了の前後、失効・再発行・削除。終了と本人の操作が同時に走った場合は、確定順に整合した結果となり、終了確定後に操作を許可しない。

### 最後の予定の取り消し（R4）

1. 有効なトークン・本人の予定・未担当を既存どおり確認する。成功済み取り消しの再送は既存の冪等処理を維持する。
2. ページから対象を除いた予定ID一覧を作り、publishedで0件になる場合は `last_published_slot`・409で拒否する。
3. 条件を満たす場合だけ、予定・秘密情報の削除、ページの予定一覧・本人予定一覧・revision更新、計測を同じトランザクションで確定する。拒否時は計測も書かない。
4. 本人用表示に取り消し可否を安全な項目として明示し、`components/recipient.tsx` は最終1件のボタンを無効化して理由を表示する。判定は画面の「これからの予定」だけの件数で代用しない。古い画面からの要求はサーバーでも拒否する。

回帰テスト：1件の拒否、2件以上の成功、再送、担当済み・別人の予定の拒否、残り2件の同時取り消し、担当登録との競合。取り消し可否はレスポンス契約の追加だけで、DB保存項目は増やさない。

## 4：検証・引き継ぎ

| 層 | 必須の確認 |
| --- | --- |
| 文書・静的検査 | `npm run docs:check`、`npm run typecheck`、`npm run lint` |
| unit / API | `npm run test`。R2〜R4の拒否・正常系・DB不変、ON/OFFと非公開項目の非露出 |
| Firestore | `npm run test:db`。本人の同時追加、古い版の保存、最終2件の同時取り消し、担当との競合、既存の担当・キャンセルとRules |
| ビルド | `npm run build:cloudflare`。期待するルートの生成、本番CSPにunsafe-evalがないこと |
| E2E | 375/390/430pxで作成→カレンダー追加→公開→匿名担当→主催者確認→キャンセル。詳細編集保存と競合、本人用発行→追加→取り消し→お休み→終了を確認 |
| 画面・アクセシビリティ | 3幅の横はみ出し、案内、モーダルのEscape・focus・キーボード、終了リンクと最後の取り消しの表示 |

E2Eはテスト用のAPP_MODE・APP_URL・本人用フラグが保証された専用ローカルサーバーで実行する。既存サーバーがある場合は停止せず、作業ツリー・ポート・ビルド出力を分離する。フラグONとOFFでサーバーを分け、既存設定を再利用して誤ったモードをテストしない。

WindowsのEPERMやエミュレーター起動失敗は環境要因として切り分ける。競合テストの409は単に再実行が通っただけで完了にせず、勝者・拒否理由・最終DB状態を検証する。新しい失敗や変更がある場合に必要な範囲を再実行する。

実装と同じ変更で `AGENTS.md`・共通要件書に終了判定・最終1件・版検証の詳細を同期し、`docs/data-model.md` に既存データの既定値とレスポンス契約を反映する。Rules・Index・移行は変更不要を確認して記録する。引き継ぎには採用SHA、変更ファイル、テスト結果、DB変更、未確認、公開状態を残す。

## 5：別途のリリース

リリース指示がある場合は、検証したコミットからPRの取り込み・Cloudflareデプロイを行い、配信SHA／Versionと公開HTTP・画面を読み戻す。本人用フラグの本番ONと実受信・ログインの再検証はそれぞれ明示された範囲で行う。ローカルテストの成功を本番反映・実機確認の完了と扱わない。
