# カレンダー起点の作成フロー設計

## 画面

1. `/create` は呼び名と期間選択を中心にした短いフォームにする。開始日と公開のひとことは折りたたみの任意入力とする。
2. 作成後は管理画面に移動する。予定一覧の前に、支援期間だけを操作できる月カレンダーを置く。
3. 日付のタップで単日追加ダイアログを開く。複数日モードは日付を選択して同じ内容の予定をまとめて追加する。
4. カテゴリ選択で推奨名を初期値にする。名前は編集でき、時刻・詳細・非公開欄は任意の折りたたみ領域に置く。
5. 0件の下書きでは「公開ページを共有」は無効にし、最初の予定の追加を案内する。既存のページ編集は詳細設定への入口として維持する。

## APIとサービス

- `POST /api/pages` は0〜60件の予定を受け、初回作成は空配列を許す。
- `PATCH /api/pages/[id]` の `add_slots` は予定追加専用とし、所有者、status、baseRevision、期間、今日以降、総数60件以下を `SupportService` のトランザクションで検証する。
- 追加する予定、`slot_secrets`、`support_pages.slotIds/revision` を同一トランザクションで書く。既存の公開投影により公開中ページでは追加予定が即時表示される。
- `setStatus(published)` は既存の空枠・期間検査を維持する。`save` は公開中ページの全予定削除を拒否する。
- Firestoreのコレクション・Rules・Index構造は変更しない。

## 安全性・互換性

- クライアントの入力はAPIとドメインスキーマで検証する。日付・件数・所有者・revisionはクライアントだけに依存しない。
- 住所、アレルギー等はこれまでどおり`slot_secrets`へ保存し、公開レスポンスの明示投影に含めない。
- `/edit`の既存編集ウィザードと担当済み予定保護を維持する。
- 既存ページを含めデータ移行は不要。
