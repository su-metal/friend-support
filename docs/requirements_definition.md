## 目的と利用者

家族・友人・知人による一時的な生活支援を、「誰が・いつ・何をするか」が分かる予定と担当に変える。最初の対象は出産・産後。Meal Trainに近い課題を扱うが、名称・UI・文章・ブランドは独自に作る。

| 利用者         | 目的                                                   | 現在の権限・利用方法                                               |
| -------------- | ------------------------------------------------------ | ------------------------------------------------------------------ |
| 主催者         | 必要な支援を予定にして共有し、担当状況を管理する       | Firebase Email Linkで認証。自分のページを管理                      |
| 支援者         | できる日にできる支援を選び、予定変更時にキャンセルする | 専用アカウント不要。名前で登録し、担当管理リンクを保持             |
| 支援を受ける人 | 身近な人から必要な生活支援を受ける                     | 主催者が了承を得てページを作る。専用アカウント・承認フローは未提供 |

成功の定義は、主催者がページを作成・公開・共有でき、支援者が登録から必要な案内の確認・キャンセルまで迷わず進め、主催者が正しい担当状況を把握できること。認知・課金の効果はまだ未検証であり、数値目標や売上を確定しない。

## 原則

身近な人同士の支援予定共有と担当調整を中心にする。支援者検索、報酬、SNS、DM、配送、支援金送金は実装しない。UIは産後から開始するが、ケース種別を汎用の型とテンプレートで保持する。

## 提供形態と事業上の優先順位

2026-10-04のユーザー決定により、スマートフォンから使えるWebアプリを主軸に進める。Firebase / Cloudflareの構成と、支援者のアカウント登録が不要な参加導線を維持する。

- 第一優先は認知と利用拡大、第二優先は収益化。検索・SNS・施設や団体からの紹介・主催者から知人への共有を集客候補とする。獲得効果は未検証。
- 現在実装済みのURLコピー、LINE共有、端末共有を利用する。LINEミニアプリとネイティブアプリは今回の実装対象に加えず、利用実績と必要性を踏まえて将来判断する。
- 公開のサービス説明や支援ガイドは、産後支援に限らない一時的な生活支援の場面を扱える。説明は現行機能で調整できる食事・買い物・送迎・家事などに限り、初期テンプレートが産後向けであることを明記する。
- 認知施策で検索対象にするのは、公開のサービス説明、支援ガイド、利用案内。個別の支援ページ、担当管理、住所・健康情報は検索対象にしない。トップページと支援ガイドに検索用メタデータ・canonicalを設定し、サイトマップには明示した公開ページだけを登録する。検索結果への登録、集客施策、獲得効果は未確認。
- 個人向けページ単位のPlus課金、組織向けPro契約、将来のギフト送客は収益仮説として扱う。価格・支払意思・継続性を検証するまで、売上見込みや需要を確定事項として扱わない。Phase 2〜6の機能フラグは引き続きOFF。
- 次の実運用準備は、Phase 1の支援通知メールの本番有効化、および利用者本人によるFirebaseログインメールからの操作確認。Resend差出人ドメイン・送信専用APIキーは設定済み。指定先への単発テストはResendでDelivered、利用者本人の受信箱でも受信確認済み。`EMAIL_FROM`未設定のため本番支援通知はOFF。

## Phase 1

- 主催者はEmail Linkでログイン。Firebase署名付きセッションCookieをHttpOnly・SameSite=Laxで保持し、署名、issuer、audience、email_verified、ユーザー無効化・失効をサーバーで確認する。
- 5ステップで作成。呼び名、期間、予定、公開プレビュー、公開。公開前は下書き。ご本人の了承を促す。
- 標準6カテゴリ。無料の期間は最大63日、1ページ60枠、1枠1人。複数日に予定を登録できる。公開説明と非公開指示を別の入力欄にする。
- `/s/[slug]` は一覧検索せず、推測しにくいURLで共有。noindex,nofollow、Cache-Control private,no-store。
- 任意の4〜8桁パスコードはPBKDF2 + ランダムソルト。解除後は期限付き署名Cookieで許可し、パスコード変更で既存許可を失効。
- 支援者は名前だけで担当可能。メールと主催者向けのひとことは任意。公開データには名前だけを表示する。
- Firestoreトランザクションで同時担当を制御。予定・担当・トークンハッシュ・通知を同時に書き込む。DB処理の失敗時は部分登録しない。
- 256bitの管理トークンを発行し、DBはSHA-256ハッシュのみ保持。メールのリンクはAES-GCMで暗号化して通知キューに保存する。管理リンクを受け取った人だけが非公開案内を表示・キャンセルできる。
- 担当後の画面で管理リンクの保存を促し、リンクのコピー、LINEで自分に送る（Keepメモへの送信を案内）、カレンダー登録用ファイル（.ics）の作成を提供する。.icsは端末内で作成し、予定名・日時・管理リンクだけを含め、住所・食事の注意・非公開指示は含めない。共有カレンダーでは他の人も管理リンクを開けることをファイル内で注意する。
- キャンセルは冪等。キャンセル後は非公開情報へのアクセスを失効し、予定を募集状態に戻す。
- 主催者は自分のページ、予定、担当者メール・メッセージを管理可能。担当確定済み予定は変更・削除を拒否し、キャンセル後に編集する。未来の予定は完了にできない。
- 主催者は公開、非公開、終了、ページ削除が可能。終了は再公開不可。ページ削除では最初に受付を止め、関連する個人情報を除去する。検索用slugも削除。
- 通知はoutboxとEmailProvider。担当確認、主催者通知、キャンセル通知、JST前日・当日8時の通知。Cloudflare Cronが10分ごとに処理。リース・同一idempotency key・最大5回の再試行を使用する。
- 計測はイベント名と許可したID、ステップ等だけ。名前、メール、住所、健康情報、管理トークンは送らない。
- Origin検証、JSONサイズ上限、Zodのサーバー検証、Firestoreによる共有レート制限、Reactによるテキストのエスケープ、CSPを実装する。
- ブラウザーからFirestoreへ直接アクセスできないRulesとし、IAMサービスアカウントをサーバーでのみ使用する。
- スマートフォンの縦型予定を中心とし、375/390/430px、キーボード、ラベル、focus、モーダルのEscapeとフォーカスを確認する。

## 運用補足

主要な状態変更の計測はFirestoreの同一commitで確定する。中断した個人情報削除はCronで再開する。レート制限データは24時間後にCronで除去する（現在のFirebaseプランはTTL非対応）。通知サービス未接続の間はメール準備中を表示し、登録確認用の管理リンクを保存するよう案内する。

## Phase 1の受け入れ条件

| ID    | 条件                                                                                                                                      |
| ----- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| AC-01 | 主催者が認証後に下書き保存・公開・共有できる。別の主催者のページ・担当情報を取得・変更できない                                            |
| AC-02 | 支援者が専用アカウントを作らず担当でき、管理リンクを受け取れる。1枠への同時登録では1人だけが確定する                                      |
| AC-03 | 公開HTML・公開APIに住所・メール・健康上の注意・非公開指示・管理トークンを含めない。担当案内は有効なトークンと担当状態で許可する           |
| AC-04 | キャンセルで枠が再募集になり、非公開案内へのアクセスが失効する。同じキャンセルの再送で状態を壊さない                                      |
| AC-05 | パスコードなしで保護されたページを閲覧できない。パスコード変更で以前の閲覧許可が失効する                                                  |
| AC-06 | 登録・キャンセル・主要計測・通知キューが同じトランザクションで確定する。通知サービス障害で成功済みの管理リンクを返せなくならない          |
| AC-07 | 接続前の通知を配信済みと表示しない。実配信の完了は送信サービス接続と指定受信者の実受信で確認し、Firebaseログインメールとは別に記録する    |
| AC-08 | 375/390/430pxで作成→公開→担当→主催者確認→キャンセルが使える。入力ラベル、キーボード操作、モーダルのフォーカスとEscapeを確認する           |
| AC-09 | デモ認証・メモリDB・実メールなしの動作は、APP_MODE=demoかつlocalhostでのみ有効。本番環境でデモ認証を利用できない                          |
| AC-10 | Phase 2〜6の機能は型・契約があっても提供済みと扱わず、未実装機能をフラグだけで公開しない                                                  |
| AC-11 | サイトマップは明示した公開案内ページだけを含み、個別支援・デモ・認証・管理ページを含まない。個別支援ページのnoindexとrobots制御を維持する |

## Phase 2〜6の土台

Plus/Pro価格は環境設定。全機能フラグの既定はOFF。Organization、OrganizationMember、PageMember、Purchase、GiftPartner、CaseTemplateの型とコレクション契約を保持する。決済とギフトのプロバイダー契約はあるが実決済・送客UIは未実装。受取人承認状態、ケース種別、必要人数はモデル上で保持する。フラグをONにしただけで未実装機能が公開されない。寄付フラグは常にfalse。

## 検証と実接続

unit/service、Firestoreエミュレーターでの競合・Rules・IDOR、ブラウザーで作成→公開→匿名担当→主催者確認→キャンセル、TypeScript、ESLint、production build、Cloudflare用buildを実施する。ローカルデモはAPP_MODE=demoかつlocalhostでのみ有効。再起動でリセットし、メールを送信しない。実メールの配信確認と、本物のEmail Linkによる本人のログイン確認は別に記録する。
